| Default on/off | Off is not the shipped default state description; toggle lives at **Settings → Library → Generate video preview thumbnails**, options: Never / scheduled task / scheduled task + on add ([Video Preview Thumbnails](https://support.plex.tv/articles/202197528-video-preview-thumbnails/), checked 2026-09-23). |
| Where it runs / trigger | Inside Plex Media Server itself; scheduled-task and/or on-add, per-library toggle available in Advanced tab ([forums.plex.tv/t/426121](https://forums.plex.tv/t/enable-video-thumbnails-vs-generate-preview-thumbnails-help/426121), checked 2026-09-23, user-reported clarifying the two related settings). |

| Servers | Plex only. |
| Known limits | CPU-bound, and per multiple forum threads generation is effectively one file at a time during the scheduled maintenance window, can take "hours or even days" for a large library on first enable (support article above). A long-standing bug (fixed by ~1.23.4 per forum reports) caused thumbnails not to generate on add until after a scheduled-task run ([forums.plex.tv/t/717756](https://forums.plex.tv/t/tv-shows-library-video-preview-thumbnail-not-being-created-at-add-time/717756), checked 2026-09-23, user-reported/unofficial fix version). Still open per a 2023 report on Synology NAS ([forums.plex.tv/t/830582](https://forums.plex.tv/t/hdr-tone-mapping-for-video-thumbnails-on-synology-again/830582), checked 2026-09-23).
| Cost/licence | **No Plex Pass required** for this specific feature — it is a plain Library setting, not listed among Plex Pass features ([Plex Pass feature matrix](https://www.plex.tv/plans/), checked 2026-09-23, lists Hardware Transcoding/Downloads/Skip Intro etc. as Pass features; preview thumbnails absent). |
| Better at | Zero setup — it's a checkbox already in the server every Plex user has. No separate host, no GPU passthrough, no path mapping to get right. |

### Jellyfin — built-in trickplay (10.9+)

| | |
|---|---|
| GPU/HW decode | Yes, optional — "Enable hardware decoding" and "Enable hardware accelerated MJPEG encoding" toggles under Playback → Trickplay ([jellyfin-web string source, LabelTrickplayAccel](https://git.uninsane.org/shelvacu-mirrors/jellyfin-web/commit/b07553a05883b07e198e3f5d150f2686b23ec13c), checked 2026-09-23). MJPEG HW encoding is "currently only available on QSV, VA-API, VideoToolbox and RKMPP" per the in-app help string (same source). |
| Default on/off | **Off by default** — GitHub issue reproduction steps instruct the user to manually check "Enable hardware decoding" ([jellyfin/jellyfin#11549](https://github.com/jellyfin/jellyfin/issues/11549), checked 2026-09-23); a Jellyfin team member in the forum says hardware acceleration for 10.9's trickplay method is "not the most efficient" and often not worth enabling ([forum.jellyfin.org, nyanmisaka reply](https://forum.jellyfin.org/t-solved-trickplay-slow-w-nvidia-gpu-nvdec), checked 2026-09-23, user-reported thread but reply is from a Jellyfin core team member). |
| Where it runs / trigger | Inside Jellyfin server; a Scheduled Task ("Generate Trickplay Images"), run on library scan or manually ([jellyfin/jellyfin#11549](https://github.com/jellyfin/jellyfin/issues/11549)). |
| Output format/location | Folder of JPG tiles packed into sprite sheets ("trickplay"), stored under Jellyfin's metadata/library directory per item, e.g. `metadata/library/<id2>/<id>/trickplay/320.bif`-style layout referenced in a Tdarr plugin discussion ([HaveAGitGat/Tdarr_Plugins#362](https://github.com/HaveAGitGat/Tdarr_Plugins/issues/362), checked 2026-09-23, user-reported path). |
| Servers | Jellyfin only. |
| Known limits | Thread count: a related library-scan concurrency default was reverted from `2× processor count` back to `1× processor count` in a 10.9-era PR, after community pushback that halving broke slower boxes ([jellyfin/jellyfin#11569](https://github.com/jellyfin/jellyfin/pull/11569), checked 2026-09-23) — note this is scan concurrency, not confirmed as the exact trickplay-thread default; trickplay itself exposes its own `ProcessThreads` option per `TrickplayOptions` ([Jellyfin TS SDK](https://typescript-sdk.jellyfin.org/interfaces/generated-client.TrickplayOptions.html), checked 2026-09-23). GPU users report HW decode both failing on some files and not measurably speeding up trickplay vs. CPU, with CPU pinned at 100% on SW fallback ([jellyfin/jellyfin#13468](https://github.com/jellyfin/jellyfin/issues/13468), checked 2026-09-23). HDR/Dolby Vision: trickplay images render "unsaturated/gray" unless "tone map" is separately enabled in transcoding settings — undocumented dependency, confirmed by a core dev in-thread ([jellyfin/jellyfin#13142](https://github.com/jellyfin/jellyfin/issues/13142), checked 2026-09-23); DV specifically showed wrong/green tones, tracked and later addressed via software tonemap for DV ([jellyfin/jellyfin#8049](https://github.com/jellyfin/jellyfin/issues/8049), PR #12571, checked 2026-09-23); still recurring per a 2026 user report of green-hued DV trickplay ([r/jellyfin](https://www.reddit.com/r/jellyfin/comments/1spfb8q/trickplay_images_with_incorrect_colors_for_dolby/), checked 2026-09-23, user-reported). |
| Cost/licence | Free, fully open source (AGPL), no paid tier. |
| Better at | Zero setup — ships in the server, generates automatically on scan if the library flag is on, no separate host or Docker image needed. |

### Emby — built-in thumbnail/BIF generation

| | |
|---|---|
| GPU/HW decode | **No.** "We use ffmpeg to create the images, and our own code to write the bif files" with no GPU option mentioned ([emby.media forum, staff reply](https://emby.media/community/topic/96831-i-just-want-to-generate-the-thumbnail-previews-bif/), checked 2026-09-23). A plugin author explains the deliberate rationale: "using hardware acceleration will slow down the extract as 99% of the time taken is the I/O reading and seeking within the file... by the time you have fed the data into the hardware and then back out again the cpu would have already scaled it" ([emby.media forum, rbjtech (MediaInfo/BIF plugin co-author)](https://emby.media/community/topic/49481-fr-use-hw-acceleration-for-chapter-image-extraction/), checked 2026-09-23, user-reported/developer explanation, not an official Emby engineering statement). |
| Default on/off | Off by default; per-library "Video Preview Thumbnails" setting, plus a "Save video preview thumbnails into media folders" sub-option ([emby.media forum](https://emby.media/community/topic/121672-how-to-stop-generating-bif-and-jpeg-file-without-turning-off-vpt/), checked 2026-09-23). |
| Where it runs / trigger | Inside Emby server; Scheduled Task "Thumbnail image extraction" (library scan or manual run); reportedly only reliably fires automatically when a file is newly detected, not retroactively for existing items missing a BIF ([emby.media forum](https://emby.media/community/topic/136433-question-about-video-preview-thumbnail-extraction-scheduled-task/), checked 2026-09-23, user-reported bug pattern). |
| Output format/location | BIF, either next to the media file (`<name>-<width>-<interval>.bif`) or under Emby's metadata dir depending on the "save into media folders" toggle ([emby.media forum](https://emby.media/community/topic/126919-how-to-rescan-thumbnail-images-after-having-replaced-video-files/), checked 2026-09-23). |
| Servers | Emby only. |
| Cost/licence | **Emby Premiere not required** — BIF/thumbnail generation is absent from the Premiere-only feature list; only Hardware Accelerated *Transcoding* (playback) and HDR Tone Mapping *when transcoding* are Premiere-gated, not preview-thumbnail generation ([Emby Premiere Feature Matrix](https://emby.media/support/articles/Premiere-Feature-Matrix.html), checked 2026-09-23). |
| Known limits | HDR: originally washed-out/no tonemap; a community plugin added HDR→SDR tonemapping, later superseded when "tonemapping is now done in the core for the BIF images" ([emby.media forum](https://emby.media/community/topic/118095-suggestion-for-bif-file-generation/), checked 2026-09-23, user-reported). File renames force full BIF regeneration since Emby treats the renamed file as new — reported as still unresolved in a Feb 2026 feature request ([emby.media forum](https://emby.media/community/topic/146119-on-demand-bif-generation-during-playback/), checked 2026-09-23, user-reported). |
| Better at | Zero setup once the library flag is on; writes BIFs Emby itself reads with no external plugin/bridge needed (contrast: this project needs Emby to just find the file next to the media). |

## Part 2 — This project's own facts (from code/docs, cited)

**Supported servers & output formats:**
- Plex: BIF bundle at `{plex_config_folder}/Media/localhost/<h0>/<h[1:]>.bundle/Contents/Indexes/index-sd.bif` — `media_preview_generator/output/plex_bundle.py:6` (template), `:140-151` (`bundle_bif_path()`).
- Emby: sidecar BIF `<basename>-<width>-<interval>.bif` next to the video — `media_preview_generator/output/emby_sidecar.py:4,48-58` (`compute_output_paths()`).
- Jellyfin: JPG tile sheets under `<basename>.trickplay/<width> - <tileW>x<tileH>/0.jpg…` — `media_preview_generator/output/jellyfin_trickplay.py:9-22, 250-257, 260-274` (`trickplay_dir()`, `sheet_dir()`). **Jellyfin plugin "Media Preview Bridge":** required only for **off-media** layout mode, not for media-adjacent mode. Purpose per `jellyfin-plugin/README.md:6-7`: "Tells Jellyfin about trickplay tiles that something else generated, so the scrubbing previews appear in the player without Jellyfin running its own ffmpeg pass." It exposes `POST /MediaPreviewBridge/Trickplay/{itemId}` (`README.md:23-24`) and requires `EnableTrickplayImageExtraction=true` + `ExtractTrickplayImagesDuringLibraryScan=false` on the Jellyfin library, with `SaveTrickplayWithMedia` matching the chosen layout mode (`README.md:48-51`). Also referenced in `docs/guides.md` (Setup Health section) as one of the per-server audits.

**GPU vendors/APIs & CPU fallback:** `media_preview_generator/gpu/detect.py:38-84` — `GPU_ACCELERATION_MAP` covers NVIDIA (CUDA), AMD (VAAPI), Intel (VAAPI), ARM (VAAPI), VideoCore (VAAPI), Apple (VideoToolbox), Windows (D3D11VA). CPU fallback: `media_preview_generator/processing/retry_cascade.py:19-20` raises `CodecNotSupportedError` so the GPU worker retries in-place on CPU; `:94-139` (`classify_cpu_fallback_reason()`) covers three trigger shapes — unsupported codec/decoder, HW-accelerator runtime error, FFmpeg signal-kill/segfault/OOM. Matches README.md:160's description of automatic, no-separate-pool CPU fallback. Note: Windows (Docker Desktop/WSL2) only accelerates NVIDIA; AMD/Intel D3D11VA and all macOS VideoToolbox are unreachable from inside Docker's Linux VM and fall back to CPU (`README.md:46`, `docs/getting-started.md` GPU Acceleration table).

**Trigger mechanisms:** Single inbound webhook `POST /api/webhooks/incoming` with vendor auto-detection — `media_preview_generator/web/webhook_router.py:1-6, 103-154` (`_classify_payload()` detects Plex multipart form, Jellyfin `NotificationType`, Emby `Event`+`Server`, Sonarr/Radarr `eventType`+file blocks, and raw `{"path": ...}`). Manual trigger via UI search/browse — `docs/guides.md:113-121`. Also: Plex Direct webhook (registers with plex.tv, requires Plex Pass) and Recently Added polling scanner for Emby/Jellyfin, per `docs/guides.md`'s Automation/Triggers section.

**HDR/Dolby Vision:** Docs at `docs/guides.md:545-600` — tone-mapping to SDR is automatic for most formats; Dolby Vision Profile 5 (no HDR10 fallback layer) needs `libplacebo`/Vulkan and is the one case with a required setup step (NVIDIA needs `NVIDIA_DRIVER_CAPABILITIES=all` for the `graphics` capability, or DV5 thumbnails render with "a bright green rectangle" — `docs/guides.md:598,628`). ## Part 3 — The one precise distinction

Candidate statements (pick one for the comparison page):

1. **"GPU-accelerated" ≠ "faster."** Jellyfin's built-in trickplay *has* a hardware-decode toggle, but it's off by default, and Jellyfin's own core team has said enabling it is often *not* faster than CPU for trickplay specifically — because it competes with live playback for the same GPU, and the 10.9 extraction method doesn't pipeline hardware decode efficiently. This project's GPU acceleration is different in kind, not just degree: it runs on a separate machine's GPU that nothing else contends for, which is the actual reason it's faster, not the mere presence of a `--hwaccel` flag.

2. **"One FFmpeg pass, every server" is about avoiding redundant *decode*, not redundant *output*.** All three servers still get their own on-disk artifact (Plex BIF bundle, Emby sidecar BIF, Jellyfin trickplay tiles) — nothing is shared or symlinked between them. The claim is specifically that the expensive step (decoding + frame-scaling the source video) happens once per file regardless of how many servers own it, per `docs/multi-server.md:6-8` and the code path in `media_preview_generator/output/*`. A reader could easily (and wrongly) assume "one pass" means one shared output file.
